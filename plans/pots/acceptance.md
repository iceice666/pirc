# pots acceptance cases (P7)

[pots](README.md) · [Product design](design.md) · [User guide](../../docs/guides/pots.md)

These cases were adopted with the conversation execution contracts (former item 7).
They are runtime and cross-client acceptance cases. **None is closed.**

The "Local evidence" column lists focused synthetic tests that already exercise
part of a case: Gateway store/API/orchestration tests, the 3 pots conformance
scenarios, and Web/Android widget tests. It does not mean the case passed. Closing
a case needs the full scenario across real Gateway/Node processes and both
clients, plus real browser/device runs where the case involves them.

| Case | Scenario and required outcome                                                                                                                                                                                                                                                                                                                                                                       | Local evidence (not acceptance)                                                                                                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P7-1 | Repeated events for one issue produce one sourced suggestion; unchanged tool progress is silent. Dismiss/snooze survives restart, and a genuinely new recurring occurrence is distinguished from a redelivery.                                                                                                                                                                                      | Dedup across overlapping scopes and reconnects; persistent dismiss/snooze controls. Recurring responsibilities do not exist yet.                                                                               |
| P7-2 | Web and App start the same suggestion concurrently with different request IDs or lost responses. One canonical task/conversation and dispatch result remain.                                                                                                                                                                                                                                        | Concurrent Track/acceptance store tests; concurrent-Start conformance scenario. No real two-client run.                                                                                                        |
| P7-3 | Opening, reading, dismissing or choosing tracking-only never starts work. Start with sufficient grants runs without redundant generic approval; missing scope shows the exact decision and does not dispatch early. Tracking without a target conversation creates no empty session; first Start creates/maps one execution conversation once, with origin and ownership still separately recorded. | Tracking creates no session; Start binds one dedicated session idempotently. Missing-scope decisions are not implemented, since there are no content grants yet.                                               |
| P7-4 | Take over A while pots coordinates A and B. Stale A follow-ups are fenced, A's running effects are truthfully reported, B continues, and an explicit Stop A reconciles only the affected execution scope. Resume B cannot release A's takeover.                                                                                                                                                     | Running-takeover and dedicated-only Stop conformance scenarios; control-generation fence tests. Stop after takeover leaves the conversation running (conformance). Two-task interplay is not covered.          |
| P7-5 | Pause observation versus coordination versus Stop. Both clients show the actual difference; restarting pots or reconnecting a device does not resume stopped tasks or replay suppressed directives.                                                                                                                                                                                                 | Durable control tests; restart recovery never replays Prepare/Start; Web/Android control views. No device run.                                                                                                 |
| P7-6 | Remove a project/grant or delete a source between observation, acceptance, dispatch and tool effect. Every boundary rechecks authority; old context cannot restore revoked rights or leak deleted preview content through a new notification.                                                                                                                                                       | Source revocation/expiry checks, revoked-source result redaction, and session-deletion fencing of Node dispatches. No OS-level mount revocation; no notifications exist yet.                                   |
| P7-7 | Exhaust budget across concurrent observations or lose the agent runtime. Pending/stale status is durable, there is no inference retry storm or implicit spending increase, and unrelated direct user work remains usable.                                                                                                                                                                           | Budget exhaustion skips new items without model calls; uncertain/restart recovery keeps the reservation without resending. No observer model exists yet.                                                       |
| P7-8 | Miss a phone push, close all Web clients, resolve a decision elsewhere, then tap the stale push. The App opens the authoritative handled result without duplicate execution; delivery failure never loses the inbox item.                                                                                                                                                                           | Not started: pots has no push or digest delivery.                                                                                                                                                              |
| P7-9 | Inject a forged user instruction through a board post/worker result or a pots-to-pots loop. It cannot acquire dispatch authority or bypass lineage/budgets.                                                                                                                                                                                                                                         | Node rejects the reserved pots-dispatch custom type on generic input; there is no REST endpoint for injecting observations or suggestions. pots-to-pots loops are impossible until autonomous dispatch exists. |
